# 2.2.3：永久记忆去重与自动合并

## 问题

`Memorize` 是追加式的：模型连着保存三次相近内容，就会得到三条永久记忆。永久记忆不参与压缩，审计又只作用于事实，于是三条记录一直常驻上下文。

## 1. 完全重复不再新增

`Memorize` 先按**去空白/标点、大小写不敏感**的方式比对同一会话内的永久记忆：

- 已存在且仍在常驻 → 直接返回该条 ID（`existing: true`），不插新记录；
- 已存在但被 `Forget` 过 → **恢复它**（`active=1`）并返回，等于"再记一次就拿回来"。

## 2. 相似永久记忆后台自动合并

新增后台任务 `dedupe`：

1. **本地筛选**：只取同一会话**活跃的永久记忆**，用字符二元组**包含度**（overlap / min 长度，至少 4 个二元组重叠）判定相似，默认阈值 `dedupe_threshold=0.25`，连通分量成簇，每簇最多 5 条。
2. **审计模型裁决**：用 `audit_model`，严格 JSON，只允许 `keep` 或 `merge`。提示词明确要求：只有**同一对象 + 同一件事/属性 + 互为重复或更正**三条同时满足才合并；主体不同（阿远 vs 小夏）、话题相近、两件不同的事一律 keep；互相矛盾按**更正**处理，只保留时间较晚的说法；合并文本必须自包含并原样保留人名、群名、数字、QQ 号与日期，不得丢关键信息。`source_ids` 必须逐字来自候选簇，否则拒绝并重试。
3. **落地（保守）**：保留**最新那条**，把它的 `summary` 更新为合并文本；其余各条 `active=0`（移出常驻上下文，**原文与版本快照都保留**）。`content` 仍是各自原文，随时可读、可恢复。

**独立任务通道**：`dedupe` 不占用 `worker_count` 的后台并发，由引擎里一个专用 worker 单独消费（并发 1），因此压缩/审计不会被合并任务拖慢，合并也不会被它们排队卡住。

**触发**：每次 `Memorize` 成功后自动入队（同会话去重 + 失败冷却）；后台每 `audit_interval` 再检查一次有 ≥2 条永久记忆的会话；后台任务页可手动「合并相似永久记忆」。

**误合并怎么恢复**：被合并的旧记忆只是 `active=0`（历史存档），在「记忆存档」里打开它点「恢复到常驻上下文」即可，原文与版本都在。

**开关**：`permanent_dedupe`（默认开）与 `dedupe_threshold`（默认 0.25，热更改）。关闭后完全不做任何检查，也不会调用模型。

## 边界

- 只处理活跃的永久记忆；不碰普通记录、事实与压缩树。
- 模型不确定就返回 `keep`，什么都不改；互相矛盾（喜欢/不喜欢）按更正处理，只保留较晚的说法。
- 不物理删除任何内容；合并动作写入 `versions`，可在记忆卡片的"最近审校"里看到理由。
