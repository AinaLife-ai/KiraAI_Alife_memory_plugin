# 2.5.0：记忆质量与成本

这一版解决两个问题：**重复记忆越攒越多**，以及**审计在后台悄悄烧钱**。

## 一、写入时合并（借鉴 KiraOS）

### 问题

审计是「定时批量复检」：候选按 `audited` 升序取，同一批都是"同龄人"，**新旧事实永远不碰面**——上个月记过的事今天又说一遍，两条会一直并存。KiraOS 的做法相反：新记忆入库前先和**最相似的几条已有记忆**比对，去重天然跨时间。

### 实现

```
压缩 / 归类 / 迁移产生一批事实
  ① 指纹精确去重（0 成本，原有）
  ② 本地找候选（0 成本）：同会话 + 同主体 + 同类别，
     bigram containment ≥ fact_merge_threshold（默认 0.25），取前 3
  ③ 没有候选 → 直接入库（绝大多数走这里，不调用模型）
  ④ 有候选 → 标记 merge_pending 并入队 fact_merge 任务
     （独立车道，不被大压缩任务挡住）
  ⑤ 一次模型调用处理最多 fact_merge_batch_clusters 组：
     模型只决定合并成什么内容，不允许 keep
  ⑥ 落库：目标取最新那条，其余软删除并写 versions 快照；
     sources/tags/relations 取并集，importance 取最大值
```

- **冲突以时间较晚的说法为准**；模型输出非法/超时 → **按时间拼接原文兜底**，保证不留近似重复。
- **跨会话合并**：仅 `profile` / `preference` / `relationship` 三类，产物落到全局作用域（`sid=global` + 全局可见来源记录），开关 `cross_session_merge` 默认开。
- **合并前不可见**：`merge_pending` 期间该事实不进检索/注入（`merge_pending_hide` 默认开），避免用户正在对话时同时看到两条重复。
- **评分放宽**：`similarity(min_overlap)` 对事实用 2（原来固定 4）。实测「她喜欢猫」vs「她喜欢猫咪」原来得 0.000（漏判），现在 1.0。
- **迁移路径**：导入时只做指纹去重，导入完成后本地聚类，只把"簇内 ≥2"的簇分批送模型，绝不逐条调用。

### 提示词与字数

| 项 | 提示词里写（软上限） | 硬上限（超了判失败重试） |
| --- | --- | --- |
| 事实合并 content | 100 | 150 |
| 事实合并 reason | 15 | 40 |
| 永久记忆合并 content | 500 | 16000（默认不动） |
| 永久记忆合并 reason | 15 | 60 |

软上限通过 `{content_max}` / `{reason_max}` 占位符在运行时替换进提示词；硬上限在解析后校验（Pydantic 的 `max_length` 是静态的，配置化上限必须后置检查）。两个提示词本身也可以在前端改。

## 二、审计节奏与成本

### 问题

原来的审计是"永动机"：每 30 分钟取 2 个最久未审的会话各审 20 条，**审完刷新时间戳，过一会儿又变成最久的**——事实不足 20 条的会话每轮都在重审同样的内容。实测 2000 条事实的库，稳态 96 次调用/天，约 50–110 万 token/天，且永不停止。

### 改动

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `audit_interval` | **7200**（原 1800） | 每 2 小时一轮 |
| `audit_recheck_days` | **7** | 同一条事实 7 天内不重复审 |
| `audit_daily_calls` | **24** | 每日调用上限，用完停到第二天 |

- 候选查询与「选哪些会话」都加了冷却过滤，**没有可审事实就不会入队、不会调用模型**。
- 迁移事实与新事实走同一套规则，没有特例。
- 实测（2000 条 + 每天 30 条新事实）：稳态从 96 次/天降到只审新事实的水平（约 1–5 次/天），且不再随库增长而增长。

## 三、配置一次性迁移

```json
{ "alife": {...}, "alife_meta": { "config_version": 2 } }
```

启动时逐级迁移，每一步只在该键**仍等于旧默认值**时改写；用户改过的一律不动，只跑一次。这样老用户不会继续用老提示词/老默认值。

## 四、事实重要度 `importance`

- `facts.importance`（1–10，默认 5）：迁移时带入 KiraOS 原值，新事实由压缩/归类模型给出；
- `records.importance`：永久记忆默认 8，压缩归档默认 0；
- 用途：画像摘要排序、检索排序、合并取最大值。

## 五、恢复历史版本

- `POST /restore {kind, target, version_id, revision}`：读快照 → 校验 revision → 写回 → **再记一条 versions**（可再退回来）；
- 记录详情、事实详情的历史版本列表带「恢复此版本」；名字历史带「设为当前名」。

## 六、画像面板与 `GetProfile`

- 人物卡片**不点开就有**：一行画像摘要（按重要度取前 3 条）+ 事实/关系/会话统计；
- 点开：按类别分组的事实、关系连线、名字历史（可编辑/恢复）；
- 新增 `GET /profile?entity_id=` 与 Bot 工具 `GetProfile`，按名字/曾用名/ID 一步拿到聚合画像；`SearchMemoryArchive` / `MemoryOverview` 保留，想继续翻原文随时可以。

## 七、模型命名

| 配置 | 显示名 | 负责 |
| --- | --- | --- |
| `compress_model` | 压缩与合并模型 | 压缩归档 + 写入时事实合并（留空用宿主默认**快速**模型） |
| `audit_model` | 审计模型 | 审计纠错 + 永久记忆合并（留空用宿主默认**主**模型） |
